  <app-architecture>
    1. Архитектура — Feature-Sliced Design, но не канонический: взят лишь принцип
       разделения на layers / slices / segments.
    2. Цепочка слоёв проекта: `app` → `features` → `entities` → `shared`.
       Зависимости строго однонаправленны — импортируем только из слоёв правее по цепочке,
       обратные импорты запрещены.
       - `app/` — роуты Expo Router (file-based), только композиция UI, без бизнес-логики
         и прямых вызовов Supabase.
       - `features/*` — пользовательские сценарии (хуки форм: RHF + zodResolver + мутация).
       - `entities/{activity,participant}` — доменное ядро: `types`, `api`, `hooks`,
         `schemas`, `mappers`, `utils`.
       - `shared/` — переиспользуемое: `ui/`, `supabase/client.ts`, `errors/`, `lib/`.
    3. Barrel-файлов (`index.ts`) в проекте нет: импортируем напрямую по пути к модулю.
       Public API slice'а — это набор его осмысленно названных файлов; не лезь во внутренности
       чужого slice в обход его API-файлов (`api.ts`, `hooks.ts`, `mappers.ts`).
    4. Имена файлов внутри slice — по смыслу, без префикса slice'а: контекст задаёт путь.
       Пример: `entities/activity/api.ts`, не `entities/activity/activity-api.ts`.
    5. Между slices одного слоя прямые зависимости запрещены: `activity` не импортирует
       `participant` и наоборот. Нужно склеить два slice — делай композицию в слое выше
       (`features` или `app`).
    6. Доступ к Supabase — только через `requireSupabase()` из `shared/supabase/client.ts`.
       Никаких прямых `createClient` в slice'ах. Env: `EXPO_PUBLIC_SUPABASE_URL`,
       `EXPO_PUBLIC_SUPABASE_KEY` (см. `.env.example`).
    7. Общий для разных частей проекта код не складываем в безымянные `utils/helpers`
       на верхнем уровне — выносим в `shared/lib/{name}` или `shared/ui/` с единой
       ответственностью и понятным неймингом.
    8. Стили — только классами NativeWind (`className`). Без `StyleSheet` и инлайновых стилей.
  </app-architecture>
